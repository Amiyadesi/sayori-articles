# 解説
AIによってコードを書くコストは、プロダクト開発の仕事を完了させるコストよりもずっと速いスピードで下がっています。この記事では、顧客のニーズから成果物のデリバリーまでを1人で一貫して責任を持つ作業単位について解説されています。

記事の冒頭では、一見するとマルチタスクの並行作業には何の問題もないように見えるものの、実際にはこの研究[https://contextcost.com/the-research](https://contextcost.com/the-research)によると、並行して作業を進めるたびにその合間でより多くの切り替え時間を消費しているというシナリオが提示されています。著者は Weinberg の古典的な経験則による見積もりを引用し、並行プロジェクトにおけるコンテキストスイッチのコストを説明しています。同時に抱えるプロジェクトが増えるにつれて、コンテキストを再読み込みするための時間が急激に跳ね上がる可能性があるというのです。

プロジェクトが2つになると本来の総時間の5分の1が奪われ、5つを同時に並行させると実に4分の3近くが奪われてしまいます。しかもこれらは単なる切り替え時間にすぎません。100%から切り替え時間を差し引き、さらにプロジェクト数で割ると、開発効率は一気に低下してしまいます。なお、このパーセンテージ自体は厳密な実験結果ではなく経験則に基づく見積もりである点には注意が必要です。そこから、本記事の核となる概念である`slice`が導入されます。

筆者の見解では、`slice`とは**垂直スライス／デリバリー可能な成果物**のことです。技術的な構造ごとに切り分けるのではなく、実際のニーズを出発点として、それを実現するために必要なすべてのレイヤーを貫通し、最終的にユーザーが実際に体感できる結果を届けるという考え方です。また、その流れでアジャイル開発のパラダイムの一つである`INVEST检查清单`についても触れられています。

続いて著者は、現時点でのAIの本当の役割について言及しています。実装フェーズの時間は大幅に短縮されたものの、意思決定フェーズで節約できる時間はごくわずかであり、最終的にはかえって全体の開発時間が延びてしまうことすらあるというのです。記事中で引用されている興味深い実験[https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)もまさにその通りでした。

著者は数年分の DORA レポートを並べることで、「AIが生産システムを混乱させる段階から、徐々にシステムへ吸収されていく」というストーリーラインを描いています。ただ、これらの年次結果は厳密な意味で同一の対象を縦断追跡したものではないため、私としてはすでに証明された因果プロセスというよりも、ひとつの傾向を示す手がかりとして捉えたいところです。

# 私の理解
実のところ、記事におけるAIの解釈は、今となってはテック界隈でも比較的よく知られた認識と言えます。つまり、AIは極めて強力な効率化ツールではあっても、本当の意味での「万能の打ち出の小槌」ではないということです。

実装フェーズにかかる時間は劇的に圧縮できますが、プロジェクト開発は実装だけで成り立っているわけではありません。要件の判断、設計、テスト、レビュー、統合、受け入れといった工程は、同じスピードでは短縮されていないのです。

そこで問題が生じます。

かつて機能開発において最もコストが高かったのは「コードを書くこと」だったかもしれません。しかしAIが登場した今、「書くこと」自体はどんどん安くなり、本当にコストが高いものへと変わってきたのは、「何を作るべきかを決めること」「生成されたものが正しいか判断すること」、そして「ひとつの物事をきちんと完了させること」です。

言い換えれば、AIは開発におけるボトルネックを消し去ったのではなく、ボトルネックの場所を移動させただけなのです。

こここそが、`slice`という概念の本当に面白いところだと私は思います。

実装コストがどんどん下がると、人は新しい罠に陥りやすくなります。「何かを始めること」が安すぎるせいで、同時にいくつものタスクを立ち上げてしまうのです。AIに機能を書かせるのはプロンプトひとつで済みますし、別のエージェントを立ち上げて別の機能を作らせるのも心理的な負担がほとんどありません。一見すると、すべてが同時に前進しているように見えます。

しかし、それらのアウトプットは最終的に誰かが理解し、テストし、修正して、受け入れるかどうかを決めなければなりません。そして、その「誰か」はたいてい自分自身です。

その結果、AIがもたらした生産性の向上は、かえって未検収のコードや未完成の機能、そして再読み込みが必要なコンテキストを大量に生み出すことになりかねません。コードが生み出されるスピードは上がっているのに、本当に「完了」したものはそれに見合うほど増えていないのです。

この観点から見ると、`slice`はこうした傾向に対する一種の制約として機能します。

作業を「データベースを実装する」「UIを書く」「APIを追加する」といった技術的なタスクに分割するのではなく、「ユーザーがこれまでできなかったひとつのことを完了できるようになる」といった、完結していて検証可能な結果としてゴールを定義するのです。

AIは依然としてその中のデータベース、UI、API、テストの実装を手助けしてくれますが、それらはもはや個別の「完了したタスク」ではなく、ひとつの結果の中に含まれる構成要素にすぎなくなります。

この話を読んで、私自身が普段 Coding Agent を使っていて感じていることを思い出しました。

以前は自分でコードを書く必要があったため、同時に進められることには自然と限界がありました。しかし今は、複数のエージェントに異なるプロジェクト――ゲーム、Webサイト、自動化スクリプト、さらには同じプロジェクト内の複数機能――を同時に修正させることができます。

表面上、私の「開発スピード」は確かに劇的に速くなりました。

けれど、エージェントが作業を終えた後、自分がその修正プロセスに関与し続けようと思えば、やはり彼らが何をしたのかを一つひとつ読み込み、既存のロジックを壊していないか確認し、テストを走らせ、それらの情報を自分の頭の中のプロジェクトモデルに再び詰め込み直さなければなりません。

本当のボトルネックは、「コードを書くのが遅いこと」から、「AIが生み出したものすべてを理解し、検収するための自分の注意力が足りないこと」へと移っているのかもしれません。

だからこそ、AI時代に重要な能力とは、同時にいくつのエージェントを動かせるかではなく、「まだ本当に終わっていないこと」を同時にいくつまで抱えるかをコントロールする力なのだと思います。

これが、私がこの記事から読み取り、得た気づきです。

`slice`が本当に最良の解決策なのかどうかは、まだわかりません。基盤のリファクタリングや技術的負債の解消、パフォーマンスの最適化などは、ユーザーが直接体感できる結果に結びつけにくい場合もありますし、1人が要件定義からデリバリーまで一貫して責任を持つことで、別の認知的負荷が生じる可能性もあります。

それでも、少なくとも非常に興味深い視点を提示してくれています。

**コードがどんどん安くなっていくこれからの時代、私たちは開発の進捗を測る基本単位を「実装」ではなく「完了」へと切り替えるべきなのでしょうか？**

これまでの私たちは、「コードを書き終えた」「ひとつの機能モジュールを作り終えた」ことを進捗と捉えがちでした。しかし、AIが実装コストを大幅に引き下げた今、そうした測り方は少しずつ通用しなくなっているのかもしれません。

本当に重要なのは、どれだけのコードを生み出したかではなく、設計、実装、検証、統合というプロセスをきちんと通り抜け、最終的に使えて、体験できて、届けられる結果になったものがいくつあるか、ということなのでしょう。

もしそうだとすれば、AI時代に本当に希少になるのは単なる実装力ではなく、スコープや注意力、そして「完了」そのものをコントロールする力なのかもしれません。

# おわりに
ふぅ……記事を読むのって本当に疲れますね……しかもこういう専門的な記事で……そのうえ長いときている。

それに何というか、正直な読後感としては、「わざわざ言うまでもないこと」に感じるか、「まったく理解できないこと」の山に感じるかのどちらかだったりします。

まあ、いわゆる「知識の呪い」というやつですよね。一度ある知識を身につけてしまうと、それを理解する前の自分の感覚を想像するのが難しくなってしまう。

でも、こうして自分の気づきや理解をシェアしようと思うなら、それをちゃんと言葉にして表現しなければなりません。そうでなければ、自分1人にしかわからない文章になってしまい、果たしてそれを「記事」と呼んでいいのかすら怪しくなってしまいます……。

アウトプットして共有するというのは、やっぱり決して簡単なことじゃないですね……。発信する怖さを乗り越えるのは、ほんの一番最初のハードルにすぎなくて、どうやって自分の視点をうまく伝え、理解を示し、筋道立てて、しかも読んでいて引き込まれる文章にするか。

なんだか、この記事で語られていたことにも少し似ています。

「書き出すこと」は、「完了」と同じではない、と。
