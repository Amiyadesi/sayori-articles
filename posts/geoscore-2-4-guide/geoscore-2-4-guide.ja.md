# GeoScore 2.4.5：自分のサイトに何が足りないのかを管理人が調べるツール

## まず開発した理由から

以前の旧バージョンの geoscore は、他の誰かがすでに開発したプロジェクトでした（[https://geoscoreapp.pages.dev/](https://geoscoreapp.pages.dev/)）。ここで試すこともできます。私もこれを使って自分のサイトのSEOをひたすら最適化しようと試みましたし、GEOやSEOなどを強化するためにwikiリストの [Amiya's Desk](https://www.wikidata.org/wiki/Q140378510) や [Amiya_desi](https://www.wikidata.org/wiki/Q140378992) を追加したりもしました。

ただ、このプロジェクトも後々になって限界が見えてきました。私の個人ブログにはよく FAQ、価格表、または Service schema を追加するよう提案が届くのですが、私のサイトには料金プランもないし、案件も受け付けていません。

ちょうどAIの利用枠にも困っていませんし、自分に必要なら、自分でフォークして開発を続けてみようと思いました。今回は分類機能をしっかり作り込みたいところです。個人ブログサイトとしては、こういったFAQ、価格表、Service schema は確かに不要だと感じています。

GeoScore は原作者のベースを元に二次開発されたものです（[https://github.com/sprawf/geoscore](https://github.com/sprawf/geoscore)）。オリジナル版の GeoScore は MIT ライセンスなので、私もこれを引き継ぐことにしました。

これは MIT ライセンスのオープンソースSEO・GEO監査ツールであり、エントリポイントとソースコードはこちらにあります。

<https://geo.sayori.org>

<https://github.com/Amiyadesi/geoscore>

完全な日本語と英語の使用ドキュメントはこちらにあります。

<https://geo.sayori.org/docs>

このツールが行うのは、すでに発見された問題、まだ分からない問題、そしてそもそも適用外の問題を切り分け、検証可能な修正手順を管理人に残し、修正の結論からmdドキュメントを生成してAIに渡し、ピンポイントで強化できるようにすることです。

## 2.4.5 の核心も、やはり結論と推測を分けること

ファクトチェックのステータスは全部で5種類のみです。

| ステータス | 意味 |
| --- | --- |
| `pass` | ページまたはレスポンスから合格を確認済み |
| `fail` | 対処が必要であるという明確な証拠がある |
| `not_applicable` | このルールは現在のサイトやページに不向き |
| `unknown` | 判断するための十分な証拠が現在ない |
| `error` | スクレイピングまたは外部サービスに問題が発生 |

適用が確認できて結論が出ている `pass` と `fail` のみが事実スコアに反映されます。

`unknown` や `error` が失敗項目にすり替わることはありませんが、これらは coverage と confidence を低下させます。

証拠が少なすぎる場合、GeoScoreあえて証拠不足と表示します。実際、これによってこの方面に多くの不足があることが分かります。

2.4 では深刻な失敗の上限キャップメカニズムが追加されました。

1つの critical（致命的）な失敗によって、該当カテゴリの最高スコアが 49 に抑えられます。さらに critical が1つ増えるごとに 10 ずつ下がり、最低 19 まで低下します。

1つの major（主要な）な失敗によって上限が 79 に抑えられ、さらに major が1つ増えるごとに 10 ずつ下がり、最低 49 まで低下します。

minor（軽微な）な失敗の影響はより軽いですが、完全に無視することはできません。

このルールは、`noindex` になっていたり、スクレイピング不能だったり、本文が抽出できないような問題を抱えたサイトが、画像 alt や OGP（Open Graph）の出来が良いというだけで、一見安全そうな高得点レポートを取得してしまうのを防ぐためです。

そのため、現在私が結果を見る順番は非常に厳格です。まず深刻な失敗と証拠を確認し、次に coverage と confidence を見、最後にようやく総合スコアを見ます。

## 73の実際のサイトがどのように校正に参加しているか

分類の正確性を自分のブログだけで証明したくはないので、現在は 73のサイトタイプ校正マトリックスを維持しています。

中身には、ニュースメディア、個人ブログ、ポートフォリオ、ドキュメントサイト、オープンソースプロジェクト、EC、コミュニティ、SaaS、専門サービス、ローカルビジネス、非営利組織、政府、大学サイトが含まれています。

各サイトについて、まず受け入れ可能なタイプの範囲を記述し、その上で現在のコードに独立してスクレイピングと判断を行わせます。

直近の2回の実行では、それぞれ「48の一致、要手動確認0、利用不可25」および「47の一致、要手動確認0、利用不可26」という結果が得られました。

2回の結果の差は1サイト分であり、その変化は新たな分類の競合によるものではなく、実際のネットワークの可用性によるものです。

スクレイピングに成功し、判断を完了したすべてのサンプルは、事前に許可されたタイプの範囲内に収まっています。

利用不可は通常、WAF、地域制限、ネットワークエラー、または認証ページが原因であり、それは分類の合格を意味せず、分類の失敗を意味するものでもありません。

この 25 のサイトはマトリックス内に保持されます。なぜなら、監査ツールが本当に向き合わなければならないのは、こうした協力的ではないページだからです。

スコアリング自体は、別途ゴールドHTMLフィクスチャを使用して校正しています。

個人ブログ、SaaS、EC、ローカルビジネス、メディア、および未知のサイトには、それぞれ固定された証拠とスコア範囲があり、深刻な失敗の上限キャップにも独自の回帰テストがあります。

実サイトマトリックスは分類のズレを発見する役割を担い、ゴールドフィクスチャはスコアの変化を再現可能にする役割を担います。この2つを混ぜ合わせて、見栄えの良い成功率にしてはなりません。

## サイトモードと単一URLモード

GeoScore には2つの使い方があります。

ドメイン名を入力するとサイトモードに入り、代表的なHTMLページを最大5つ抽出します。

最初にトップページが読み込まれ、Aboutページが発見されれば一緒に加わります。その後、サイトマップやトップページの内部リンクから、パスの種類に応じて他のサンプルが選択されます。

5ページというのは全サイトワーカー（クローラー）ではなく、1回の監査を説明可能で再実行可能な範囲に抑えるためのものです。

そのため、レポート内のサンプルリストを見る価値があります。今回の結論が一体どの数ページから導き出されたのかが分かるからです。

もし新しい記事1本、改修したばかりのランディングページ、または特定の特集ページだけをチェックしたい場合は、完全なURLを貼り付けることができます。

これにより単一URLモードに入り、対象ページに重点を置いた審査が行われます。

対象ページがトップページではない場合でも、ツールが必要に応じてトップページを読み込んでコンテキストを構築するため、AIについて書いた記事1本だけでサイト全体をSaaSと誤認するのを防ぎます。

私は普段、まずドメインを実行してサイト全体の共通設定とサイトプロファイルを確定させ、その上で本当に修正したいページに対して単一URLモードを1回実行します。

## まず、自分を何だと認識したかを確認する

監査が完了したら、すぐに総合スコアを凝視してはいけません。

まずはサイトプロファイルを確認してください。
![[Pasted image 20260720112010.png|width=360|align=center]]

ここには、サイトタイプ、エンティティ、言語、ルートドメイン、サンプリングページ、識別信頼度、および分類の証拠が表示されます。

プロファイルは、JSON-LD、canonical、タイトル、ナビゲーション、ページ構造を優先して根拠にし、本文のキーワードは弱いシグナルとしてしか扱いません。

これは、個人ブログがSaaSと判定されたり、ドキュメントサイトがECと判定されたり、記事サイトに商用schemaが無理やり押し込まれたりするのを防ぐためです。

タイプが実際に間違っている場合は、今回の監査に限りタイプのヒントを与えることができます。「タイプを修正」をクリックして正しいタイプを選択してください。

これはシステム全体に永続的なルールを書き込むことにはならず、他のウェブサイトにも影響しません。

## ページが取得できないとき、なぜそのままゴリ押しして計算してはいけないのか

実際のウェブサイトは、しばしば本文を直接返してくれません。

Cloudflareのチャレンジを返すサイトもあれば、ログインや同意ページを返すサイトもあり、SiteGroundではHTTP 202で `/.well-known/sgcaptcha/` の認証ページが返されることもあります。

これらのページもHTMLに見えますが、これらを使ってSEO監査を行っても、認証ページに関する偽のレポートが得られるだけです。

2.4.5 はまずこうした中間ページを識別し、HTTP 202や空の認証ページをスクレイピング成功として扱わなくなりました。

通常のHTTP確認でチャレンジ、再試行可能なネットワークエラー、またはJavaScriptの空の殻に遭遇した場合、トップページに対してCloudflare Browser Runによるフォールバックを1回使用できます。

この試行には明確に20秒の予算が割り当てられます。

ページナビゲーションに最大16.5秒を使用し、`load` イベントのあとにさらに1.5秒かけて通常のhydrationを完了させ、最後に2秒を残してHTMLを取得します。

以前 `networkidle2` を使用していたときは、分析スクリプトや継続的なリクエストによってページがいつまでもネットワークのアイドル状態を迎えられず、最終的に予算全体を使い果たしてしまうことがありました。

現在はバックグラウンドのネットワークが完全に静かになるのを待たなくなりましたが、それでもレンダリング結果がチャレンジ、エラーページ、または本文のないJavaScriptの空の殻になっていないかはチェックします。

フォールバックがやはり失敗した場合、GeoScore はページを `unknown` または `error` の状態のままにし、総合スコアはそのまま証拠不足になり得ます。

2.4.5 は同時に、監査キャッシュを `v24` に引き上げました。

これにより、デプロイ後に旧バージョンが残したタイムアウトや認証ページの結果にヒットし続けることがなくなり、古いキャッシュは元のTTLに従って自然に期限切れになります。

## カスタムAPIはどう使うか

トップページの入力欄の下には、デフォルトで折りたたまれたカスタムAPIパネルがあります。

これはオプション機能であり、事実監査が完了した後に、Evidence Mapのために回答の観察を1回行う場合にのみ使用します。

API Key、HTTPS Base URL、および model を入力すると、モデルのリストを取得することも、既知のモデルを手動で直接入力することもできます。

Base URLの末尾に手動で `/v1/models` を繋げる必要はありません。

入力したのが `https://api.example.com` である場合、GeoScore は自動的に `https://api.example.com/v1` に補完します。

誤って `/models` や `/chat/completions` まで一緒に貼り付けてしまった場合でも、対応するAPIのルートパスに一度戻ってからリクエストを送信します。

3つのフィールドは一緒に記入する必要があり、1つでも欠けるとリクエストを送信できません。

監査を開始する前に、ブラウザはこれらをクリアします。これらがブラウザのストレージ、URL、またはダウンロードされるレポートに書き込まれることはありません。

サーバー側でもこれらを1回限りのリクエストの設定としてのみ扱い、監査終了後に永続化されることはありません。

だからといって、画面録画やライブ配信で実際のKeyを晒して良いわけではありません。機密情報はやはり隠すべきです。

リクエストが完了すると、最新のAPIの回答が Evidence Map の一番上に直接表示されます。

ここでは、クエリ、モデル、ステータス、時刻、所要時間、回答の本文、引用数が確認でき、完全な回答と引用はさらに展開して見ることができます。

カスタムAPIが成功しても失敗しても、事実スコアが変更されることはありません。

私はこの機能を、事実に関する問題が一通り処理されてから使うように残しています。

まずページ自体の問題を確認し、それから外部検索や回答の観察を確認する。順番を逆にしてしまうと、生成されたテキストに簡単に流されてしまいます。

## モニタリング用Tokenの本当の役割とは

監視プロジェクトを作成すると、project ID と management token の2つが手に入ります。

project ID はプロジェクトを識別するために使用され、Token はあなたがプロジェクトを読み取る権限、クエリを変更する権限、スナップショットを実行する権限、履歴を閲覧する権限、Tokenをローテーションする権限、またはプロジェクトを削除する権限を持っていることを証明します。

サーバー側には保護されたハッシュのみが保存され、生のTokenは作成時またはローテーション時に一度だけ表示されます。

そのため、最初に手に入れたらまずは自分のパスワードマネージャーにコピーしておくべきです。

ブラウザやデバイスを変えるときは、「既存の監視プロジェクトに接続」に project ID と Token を入力すれば、クエリ、履歴、プロジェクトの状態を再び読み込むことができます。

ページはデフォルトではTokenを保存しません。

「このデバイスに保存する」を明示的にクリックした場合にのみ、現在のブラウザのローカルストレージに保存され、いつでも「このデバイスの記憶を消去」をクリックして消すことができます。

もしTokenがスクリーンショット、チャット履歴、または公開ログに映り込んでしまった場合は、すぐにローテーションしてください。古いTokenは即座に無効になります。

Docsページには、そのままコピーして使える `curl` のリクエストと公開APIの説明が記載されています。

## メール監視の仕組み

監視プロジェクトにはメールアドレスを入力して認証を完了させることができます。

比較可能なベースラインが確立されており、スコアリングのバージョンが同じで、coverage が十分であり、かつスコアに実際に変動があった場合にのみ、システムはアラートの送信を試みます。

初回実行時、スコアリングバージョンの変更時、または証拠不足時はスナップショットを保存するだけで、増減のアラートは発報されません。

現在のメールアダプターはメインの送信チャネルを優先しますが、認証、レートリミット、ネットワーク、または上流の障害が発生した場合には、管理人自身の固定送信メールサービスに切り替えることができます。

メールの成否にかかわらず、すでに完了した監査のスナップショットは最初に保存されます。

## 完全なMarkdown修正レポートのダウンロード

監査の実行後、ファイルを1つずつ生成しなくても、完全なMarkdown修正レポートをまとめてダウンロードできます。

レポートには、サイトプロファイル、サンプリングページ、スコアと上限の理由、すべての失敗の証拠、未知のエラーおよび外部エラー、オプションモジュールのステータス、グループ化された修正タスク、検証手順が含まれます。

レポートの最後には、開発用AI向けの handoff prompt も用意されています。

これを Codex、Claude、その他のプログラミングアシスタントに渡すことができますが、モデルに対しては既存の証拠のみを使用し、存在しない価格、サービス、住所、エンティティ、著者、統計ソースを勝手に捏造しないよう要求します。

私は普段、このMarkdownをサイトのコードリポジトリの隣に置き、プログラミングアシスタントに該当URLのソースファイルをまず特定させ、その上で自分でdiffをレビューするようにしています。

## 実際の使用手順の流れ

1. <https://geo.sayori.org>，先用站点模式审首页域名 を開く
2. サイトプロファイルとサンプリングページがズレていないか確認する
3. ファーストビューでスクレイピング失敗と表示されている場合は、まずページ取得の証拠を確認し、存在しないスコアを無理に解説しない
4. coverage、confidence、および3つの優先アクションを確認してから、総合スコアに参考価値があるかを判断する
5. critical と major の失敗を優先して処理し、該当ページのソースファイルやCMSテンプレートに戻って修正する
6. パフォーマンスの問題については、モバイルとデスクトップの両方に実際のPageSpeedデータがあることを個別に確認する
7. 事実に関する問題の処理が終わってから、必要に応じて Evidence Map を実行するか、カスタムAPIを1回入力する
8. Markdownレポートをダウンロードし、開発用AIに渡して2回目の特定を行わせ、自分で変更内容をレビューしてからデプロイする
9. 継続的な監視が必要な場合のみ監視プロジェクトを作成し、project ID と Token をパスワードマネージャーに保存する
10. ボタンやインターフェースが不明な場合は <https://geo.sayori.org/docs> を開く
11. デプロイ後、同じURLを再度監査し、失敗の証拠が本当に消えたことを確認する

## このツールにできないこと

GeoScore は無限の深さを持つクローラーではなく、5ページのサンプルがすべてのURLを代表することはできません。

また、Search Console、サーバーログ、実際のユーザーデータ、あるいは人間によるコンテンツの判断の代わりになることもありません。

WAF、ログインウォール、認証ページ、または地域制限によってブロックされたページについては、レポートが `unknown` や `error` しか返せない場合があります。

このような場合に、スコアを稼ぐためにセキュリティポリシーをオフにしてはなりません。

あるコンシューマー向けAI製品があなたのサイトを実際に引用していることを、根拠なく断定することも到底できません。

私にとって、こうした境界線こそがかえってレポートを使いやすくしてくれている要素です。

監査ツールとは、何を知っていて何を知らないのかを明確に語るべきであり、残りの作業はサイトの管理者が自ら検証すればよいのです。

## 続けて読む

まだサイトを構築していない場合は、[[astro-mizuki-blog-from-zero|シンプルなブログテンプレート]] から始めることができます。ドメイン、ホスティング、画像ストレージなどは [[cloudflare-free-tier-developer-guide|Cloudflareの無料枠]] に置いています。

スクレイピングやインデックス作成のほかにも、記事を読む際の体験そのものを私は調整しており、その試行錯誤の過程は [[blog-style-change|ブログのスタイル改版の記録]] に書いてあります。
