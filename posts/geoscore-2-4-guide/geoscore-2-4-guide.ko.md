# GeoScore 2.4.5: 웹master가 자기 사이트에 뭐가 부족한지 확인하기 위해 쓰는 도구

## 제작 이유부터 먼저

예전 버전의 geoscore는 다른 사람이 이미 개발해 둔 프로젝트였는데([https://geoscoreapp.pages.dev/](https://geoscoreapp.pages.dev/)), 여기서도 한번 체험해 볼 수 있습니다. 저도 이걸로 제 사이트의 SEO를 계속 최적화하려고 시도해 봤고, 심지어 GEO와 SEO 등을 강화하려고 wiki 목록인 [Amiya's Desk](https://www.wikidata.org/wiki/Q140378510)와 [Amiya_desi](https://www.wikidata.org/wiki/Q140378992)까지 추가해 보았죠.

하지만 이 프로젝트도 시간이 지나면서 한계를 드러내기 시작했습니다. 제 개인 블로그에는 자꾸 FAQ, 가격표(Price table)나 Service schema를 추가하라는 제안이 들어오는데, 제 사이트는 요금제도 없고 외주 프로젝트도 안 받거든요.

마침 제게 AI 크레딧도 부족하지 않겠다, 제 필요에 맞으니 직접 2차 개발을 해보기로 했습니다. 이번에는 분류(classification) 기능을 확실히 다듬어야겠다고 마음먹었습니다. 개인 블로그 사이트 입장에서 이런 FAQ 가격표나 Service schema는 정말 쓸데없으니까요.

GeoScore는 원작자의 기반 위에서 2차 개발된 도구입니다([https://github.com/sprawf/geoscore](https://github.com/sprawf/geoscore)). 원본 GeoScore는 MIT 라이선스라서 저도 그것을 계승하기로 했습니다.

MIT 라이선스의 오픈소스 SEO 및 GEO 감사(audit) 도구이며, 진입점과 소스 코드는 여기 있습니다.

<https://geo.sayori.org>

<https://github.com/Amiyadesi/geoscore>

상세한 한글 및 영문 사용 설명서는 여기에 있습니다.

<https://geo.sayori.org/docs>

이 도구가 하는 일은 이미 발견된 문제, 아직 모르는 문제, 애초에 전혀 적용되지 않는 문제를 분리하고, 검증 가능한 수정 경로를 웹master에게 남겨준 뒤, 수정 결론을 md 문서로 생성해 AI에게 전달함으로써 맞춤형 개선을 하도록 돕는 것입니다.

## 2.4.5의 핵심은 여전히 결론과 추측을 먼저 구분하는 것

모든 팩트 체크(fact check) 항목은 다섯 가지 상태만 가집니다.

| 상태 | 의미 |
| --- | --- |
| `pass` | 페이지나 응답에서 통과된 것이 이미 확인됨 |
| `fail` | 처리해야 한다는 명확한 증거가 있음 |
| `not_applicable` | 이 규칙은 현재 사이트나 페이지에 맞지 않음 |
| `unknown` | 현재 판단하기에 충분한 증거가 없음 |
| `error` | 크롤링이나 외부 서비스에 문제가 생김 |

적용 대상임이 확인되고 결론이 있는 `pass`와 `fail`만 사실 점수(fact score)에 반영됩니다.

`unknown`과 `error`은 실패 항목으로 둔갑하지는 않지만, coverage(커버리지)와 confidence(신뢰도)를 떨어뜨립니다.

증거가 너무 적을 때 GeoScore는 차라리 증거 부족을 표시하는데, 사실 이 상태만 봐도 이 부분에 문제가 많다는 것을 짐작할 수 있습니다.

2.4 버전에서는 심각한 실패(critical) 상한선 메커니즘이 추가되었습니다.

Critical 실패가 하나 있으면 해당 카테고리의 최고 점수가 49점으로 깎이고, critical이 하나 늘어날 때마다 10점씩 더 내려가서 최저 19점까지 떨어집니다.

Major 실패가 하나 있으면 상한선이 79점으로 깎이고, major가 하나 늘어날 때마다 10점씩 더 내려가서 최저 49점까지 떨어집니다.

Minor 실패는 영향이 더 가볍지만, 그렇다고 완전히 무시할 수는 없습니다.

이 규칙은 `noindex` 때문에 크롤링을 할 수 없거나 본문을 추출할 수 없는 문제가 있는 사이트가 이미지 alt나 Open Graph를 잘 만들었다는 이유로 겉보기엔 안전해 보이는 높은 점수 리포트를 받는 것을 방지하기 위한 것입니다.

그래서 요즘 저는 결과를 보는 순서가 아주 깐깐합니다. 심각한 실패와 증거를 먼저 보고, 그다음에 coverage와 confidence를 보며, 마지막에 총점을 봅니다.

## 73개의 실제 사이트는 어떻게 보정(calibration)에 참여하는가

제 블로그 하나만 가지고 분류가 정확하다고 우기고 싶지 않아서, 현재 73개 사이트 유형 보정 매트릭스를 유지하고 있습니다.

거기에는 뉴스 미디어, 개인 블로그, 포트폴리오, 문서 사이트, 오픈소스 프로젝트, 이커머스, 커뮤니티, SaaS, 전문 서비스, 로컬 비즈니스, 비영리 조직, 정부 및 대학 사이트가 포함되어 있습니다.

각 사이트별로 허용 가능한 유형 범위를 먼저 작성한 뒤, 현재 코드가 독립적으로 크롤링하고 판단하게 합니다.

최근 두 번의 실행에서는 각각 48개 일치, 0개 수동 검토 필요, 25개 사용 불가와 47개 일치, 0개 수동 검토 필요, 26개 사용 불가 결과가 나왔습니다.

두 결과의 차이는 단 한 개의 사이트뿐이며, 이 변화는 새로운 분류 충돌이 생겨서가 아니라 실제 네트워크 가용성 때문에 발생한 것입니다.

성공적으로 크롤링하고 판단을 마친 모든 샘플은 사전에 허용된 유형 범위 내에 떨어집니다.

사용 불가 상태는 주로 WAF, 지역 제한, 네트워크 오류 또는 인증 페이지 때문에 발생하며, 이것이 분류 통과를 의미하지도 않고 분류 실패를 의미하지도 않습니다.

이 25개의 사이트는 매트릭스에 그대로 유지됩니다. 감사 도구가 실제로 마주해야 하는 대상이 바로 이런 비협조적인 페이지들이기 때문입니다.

점수 자체는 별도로 골든 HTML fixture를 사용해 보정합니다.

개인 블로그, SaaS, 이커머스, 로컬 비즈니스, 미디어, 알 수 없는 사이트 모두 고정된 증거와 점수 구간을 가지며, 심각한 실패 상한선도 독립적인 회귀 테스트(regression test)를 거칩니다.

실제 사이트 매트릭스는 분류 편향을 찾아내는 역할을 하고, 골든 fixture는 점수 변화를 재현 가능하게 만드는 역할을 합니다. 이 두 가지를 보기 좋은 성공률 하나로 뭉뚱그려서는 안 됩니다.

## 사이트 모드와 단일 URL 모드

GeoScore에는 두 가지 사용법이 있습니다.

도메인을 입력하면 사이트 모드로 진입하며, 대표성 있는 HTML 페이지를 최대 5개까지 추출합니다.

홈페이지를 가장 먼저 읽어 들이고, About 페이지를 찾으면 함께 포함시킨 뒤, sitemap이나 홈페이지 내부 링크에서 경로 유형에 따라 다른 샘플들을 골라냅니다.

5페이지라는 건 전체 사이트 크롤러가 아니라, 감사를 설명 가능하고 다시 실행할 수 있는 범위 안으로 통제하기 위함입니다.

따라서 리포트 안의 샘플 목록은 살펴볼 가치가 있습니다. 이번 결론이 정확히 어떤 페이지들에서 나왔는지 알려주니까요.

만약 새 글 하나, 방금 수정한 랜딩 페이지, 혹은 특정 특집 페이지만 검사하고 싶다면 전체 URL을 붙여넣으면 됩니다.

그러면 단일 URL 모드로 진입하여 타겟 페이지에 집중합니다.

타겟 페이지가 홈페이지가 아니더라도 도구는 필요할 때 홈페이지를 읽어들여 문맥을 파악하며, AI에 관한 글 하나만 보고 전체 사이트를 SaaS로 오인하는 것을 방지합니다.

저는 보통 도메인으로 먼저 실행해서 전체 사이트의 공통 설정과 사이트 이미지를 확인한 뒤, 실제로 수정할 페이지에 대해 단일 URL 모드를 한 번 더 돌립니다.

## 페이지를 가져오지 못할 때, 계속 억지로 계산하면 안 되는 이유

실제 웹사이트는 종종 본문을 곧바로 반환하지 않습니다.

어떤 사이트는 Cloudflare challenge를 반환하고, 어떤 사이트는 로그인이나 동의 페이지를 반환하며, SiteGround 같은 곳은 HTTP 202로 `/.well-known/sgcaptcha/` 인증 페이지를 반환할 수도 있습니다.

이런 페이지들도 겉보기엔 HTML이지만, 이걸로 SEO 감사를 해봤자 인증 페이지에 대한 가짜 리포트밖에 나오지 않습니다.

2.4.5 버전은 이런 중간 페이지들을 먼저 인식하며, HTTP 202나 빈 인증 페이지를 크롤링 성공으로 취급하지 않습니다.

일반적인 HTTP 확인 과정에서 challenge, 재시도 가능한 네트워크 오류, 또는 JavaScript 빈 껍데기를 만나면 홈페이지는 Cloudflare Browser Run을 한 번 사용하여 대체(fallback)할 수 있습니다.

이번 시도에는 명확한 20초의 예산(budget)이 주어집니다.

페이지 네비게이션에 최대 16.5초를 사용하고, `load` 이벤트 후에 일반 hydration을 완료할 수 있도록 1.5초를 더 준 뒤, 마지막으로 HTML을 가져오는 데 2초를 남겨둡니다.

이전에 `networkidle2`를 사용했을 때는 분석 스크립트와 지속적인 요청 때문에 페이지가 네트워크 유휴 상태(network idle)를 계속 기다리게 만들고, 결국 전체 예산을 소모해 버리곤 했습니다.

이제는 백그라운드 네트워크가 완전히 조용해질 때까지 기다리지 않지만, 렌더링된 결과가 challenge인지, 오류 페이지인지, 혹은 본문이 없는 JavaScript 빈 껍데기인지는 여전히 확인합니다.

대체 시도마저 실패하면 GeoScore는 해당 페이지를 `unknown` 또는 `error` 상태로 남겨두며, 총점은 곧바로 증거 부족 상태가 될 수 있습니다.

2.4.5 버전은 동시에 감사 캐시(cache)를 `v24`로 올렸습니다.

이렇게 배포되면 이전 버전이 남겨둔 타임아웃이나 인증 페이지 결과가 계속 히트(hit)되지 않으며, 기존 캐시는 원래의 TTL에 따라 자연스럽게 만료됩니다.

## 커스텀 API는 어떻게 써야 할까

홈페이지 입력창 아래에는 기본적으로 접혀 있는 커스텀 API 패널이 있습니다.

이는 선택 기능으로, 사실 감사(fact audit)가 끝난 후 Evidence Map을 위해 답변 관찰(answer observation)을 한 번 수행할 때만 사용됩니다.

API Key, HTTPS Base URL, model을 입력하면 모델 목록을 불러올 수도 있고, 알려진 model 이름을 직접 수동으로 입력할 수도 있습니다.

Base URL 뒤에 수동으로 `/v1/models`을 붙일 필요는 없습니다.

제가 입력한 값이 `https://api.example.com`이라면 GeoScore가 자동으로 `https://api.example.com/v1` 형태로 보정해 줍니다.

실수로 `/models`나 `/chat/completions`을 함께 붙여넣더라도, 도구가 먼저 해당 API 루트 경로로 되돌아간 뒤에 요청을 보냅니다.

세 필드는 모두 함께 입력해야 하며, 하나라도 누락되면 요청을 보낼 수 없습니다.

감사를 시작하기 전에 브라우저는 이 값들을 비우며, 브라우저 스토리지, URL, 다운로드되는 리포트에 저장되지 않습니다.

서버 또한 이 값들을 단일 요청을 위한 설정으로만 취급하며, 감사가 끝난 뒤에 지속해서 저장(persistence)하지 않습니다.

그렇다고 녹화나 라이브 방송에서 진짜 Key를 화면에 보여줘도 된다는 뜻은 아니니, 민감한 정보는 여전히 가려야 합니다.

요청이 완료되면 최신 API 답변이 Evidence Map 최상단에 바로 표시됩니다.

여기서 쿼리, 모델, 상태, 시간, 소요 시간, 답변 본문, 인용 횟수를 볼 수 있으며, 전체 답변과 인용 내용은 계속 펼쳐서 확인할 수 있습니다.

커스텀 API가 성공하든 실패하든 사실 점수(fact score)는 변경되지 않습니다.

저는 팩트 관련 문제가 한 차례 처리된 뒤에야 이 기능을 사용합니다.

페이지 자체의 문제를 먼저 보고, 외부 검색과 답변 관찰은 그 다음에 봐야 합니다. 순서가 뒤바뀌면 생성된 텍스트 몇 줄에 쉽게 휩쓸려 버리거든요.

## 모니터링 토큰은 도대체 무슨 소용인가

모니터링 프로젝트를 생성하고 나면 project ID와 management token 두 가지를 받게 됩니다.

project ID는 프로젝트를 식별하는 데 쓰고, 토큰은 프로젝트를 읽을 권한이 있거나, 쿼리를 수정하거나, 스냅샷을 실행하거나, 히스토리를 보거나, 토큰을 교체(rotate)하거나, 프로젝트를 삭제할 권한이 있음을 증명하는 데 씁니다.

서버에는 보호 처리된 해시(hash)만 저장되며, 원본 토큰은 생성되거나 교체될 때 딱 한 번만 표시됩니다.

그러므로 처음 발급받았을 때 비밀번호 관리자(password manager)에 가장 먼저 복사해 두어야 합니다.

다른 브라우저나 기기로 바꿀 때는 '기존 모니터링 프로젝트 연결'에서 project ID와 토큰을 입력하여 쿼리, 히스토리, 프로젝트 상태를 다시 불러올 수 있습니다.

페이지는 기본적으로 토큰을 저장하지 않습니다.

'이 기기에 저장'을 명확히 클릭했을 때만 현재 브라우저의 로컬 스토리지에 저장되며, 언제든지 '이 기기 잊기'를 누를 수 있습니다.

만약 토큰이 스크린샷, 채팅 기록, 공개 로그 등에 노출되었다면 즉시 교체하세요. 기존 토큰은 즉시 무효화됩니다.

Docs 페이지에는 바로 복사해서 쓸 수 있는 `curl` 요청 및 공개 API 설명이 나와 있습니다.

## 이메일 모니터링은 어떻게 작동할까

모니터링 프로젝트에 이메일을 입력하고 인증을 마칠 수 있습니다.

비교 가능한 베이스라인이 구축되어 있고, 점수 버전이 동일하며, coverage가 충분하고, 점수가 실제로 변했을 때만 시스템이 알림 발송을 시도합니다.

첫 실행, 점수 버전 변경, 또는 증거 부족 상태일 때는 스냅샷만 저장하고 등락 경고를 만들지 않습니다.

현재 이메일 어댑터(adapter)는 메인 발송 채널을 우선 사용하며, 인증, 속도 제한(rate limit), 네트워크 또는 상위 서비스 장애가 발생할 경우 웹master 고유의 고정 발송 서비스로 전환할 수 있습니다.

이메일 성공 여부와 관계없이 이미 완료된 감사 스냅샷은 우선 저장됩니다.

## 전체 Markdown 수정 리포트 다운로드하기

감사를 마친 후 전체 Markdown 수정 리포트를 한 번에 다운로드할 수 있으며, 항목별로 파일을 생성할 필요가 없습니다.

리포트에는 사이트 이미지, 샘플링된 페이지, 점수 및 상한선 원인, 모든 실패 증거, 미지의 오류 및 외부 오류, 모듈별 상태, 그룹화된 수정 작업, 검증 단계가 포함됩니다.

리포트 마지막에는 개발용 AI에게 전달하는 handoff prompt도 있습니다.

이것을 Codex, Claude 또는 다른 프로그래밍 어시스턴트에게 전달할 수 있지만, 모델에게는 이미 존재하는 증거만 사용하도록 요구하며 존재하지 않는 가격, 서비스, 주소, 엔티티, 작성자, 통계 출처를 지어내지 못하게 합니다.

저는 보통 이 Markdown 파일을 사이트 코드 저장소 옆에 두고, 프로그래밍 어시스턴트가 대응하는 URL의 소스 파일을 먼저 찾아내게 한 뒤 diff를 직접 검토합니다.

## 실제 사용 순서

1. <https://geo.sayori.org>，先用站点模式审首页域名 열기
2. 사이트 이미지와 샘플링된 페이지가 엉뚱한 곳을 가리키고 있지 않은지 확인하기
3. 첫 화면에 크롤링 실패가 표시되면, 존재하지 않는 점수를 계속 설명하려 하지 말고 페이지 획득 증거를 먼저 보기
4. coverage, confidence, 세 가지 우선 행동을 본 뒤 총점이 참고 가치가 있는지 결정하기
5. critical 및 major 실패를 먼저 처리하고, 해당 페이지의 소스 파일이나 CMS 템플릿으로 돌아가서 수정하기
6. 성능 문제는 모바일과 데스크톱 모두 실제 PageSpeed 데이터가 있는지 개별적으로 확인하기
7. 팩트 관련 문제가 처리된 후 필요에 따라 Evidence Map을 실행하거나 커스텀 API를 한 번 입력하기
8. Markdown 리포트를 다운로드하여 개발용 AI에게 두 번째 위치 지정을 맡기고, 직접 변경 사항을 검토한 후 배포하기
9. 지속적인 관찰이 필요할 때 모니터링 프로젝트를 생성하고, project ID와 토큰을 비밀번호 관리자에 저장하기
10. 버튼이나 인터페이스를 잘 모르겠다면 <https://geo.sayori.org/docs> 열기
11. 배포 후 동일 URL을 다시 감사하여 실패 증거가 실제로 사라졌는지 확인하기

## 이 도구가 할 수 없는 것

GeoScore는 무한 깊이의 크롤러가 아니며, 5개의 샘플은 모든 URL을 대표할 수 없습니다.

Search Console, 서버 로그, 실제 사용자 데이터, 수동 콘텐츠 판단을 대체하지도 않습니다.

WAF, 로그인 벽, 인증 페이지, 지역 제한에 가막힌 페이지는 리포트가 `unknown` 또는 `error`밖에 제공하지 못할 수 있습니다.

이럴 때는 점수를 올리기 위해 보안 정책을 꺼버려서는 안 됩니다.

소비자용 AI 제품이 실제로 당신의 사이트를 인용했는지 무에서 유를 창조하듯 확인해 주는 것은 더더욱 불가능합니다.

오히려 제게는 이러한 한계들 덕분에 이 리포트가 더 쓸만해졌습니다.

감사 도구라면 아는 것과 모르는 것을 명확히 말해 주어야 하고, 남은 일은 사이트 운영자가 직접 검증해야 하니까요.
